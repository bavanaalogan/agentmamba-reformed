# Experiments

All numbers in this project are produced by the commands below and read from `experiments/results/`.
`comparison.md` is generated by `scripts/evaluate.py` from the latest run of each test-split method.

## Protocol
1. Generate and validate the benchmark (seed 13). Extract features.
2. Train the gates (train split), select C and the threshold (val). Train the intent classifier and controller (train),
   tune the controller threshold (val).
3. **Development runs on the validation split** (`--split val`) for error analysis and bug fixing.
4. **Final runs on the test split.** No configuration was chosen from test results. The primary budget of 10% was
   fixed beforehand.

**Deviation, recorded honestly.** The first two test runs (E, and H as a cached duplicate of E) exposed a
parsing bug: work orders on ladles were answered with a clarification request. I found it while reading those test
errors, fixed it (with a regression test), retrained the controller, moved development to the validation split, and
regenerated every test run. The pre-fix runs are kept in `experiments/archive/`. The fix is a correctness fix (the
question shape exists in all splits) and not a tuned parameter, but it was triggered by looking at test outputs.

## Commands
```powershell
$py = ".\.venv\Scripts\python.exe"
& $py scripts\run_experiment.py --data data\synthetic\main --split val --methods E_agentmamba,B_storeall_rag
& $py scripts\run_experiment.py --data data\synthetic\main --methods all
& $py scripts\run_experiment.py --data data\synthetic\main --sweep
& $py scripts\run_public_experiment.py
& $py scripts\evaluate.py
& $py scripts\benchmark_latency.py --n 40        # cold-cache latency (run twice; report medians)
```
`scripts/run_all_test.ps1` launches the test-split methods and the sweep as two parallel worker chains. The last
sweep runs (heuristic/random 25–50%, store-all) were relaunched in four processes with `--sweep-budgets` and
`--threads 4`, because random-policy memories produce many distinct candidates and are slow to score (about 18 s per question).
Thread count does not change results, and memories and Mamba scores are deterministic.

Note on latency fields inside experiment runs: Mamba scores are memoized across runs, so `latency` in those summaries
mostly measures cache hits. Efficiency claims use only the cold-cache benchmark.
Each run directory contains `config.json` (full config, spec, seed, dataset manifest, model IDs, gate version,
environment), `predictions.jsonl` (full decision trace per question), `rows.jsonl` (scored rows), `summary.json` and
`summary.md`. Run directories are timestamped and never overwritten.

## Metric definitions (computed in `src/agentmamba/evaluation/`)
**Correctness per question** depends on the gold answer kind:
- `value`: answered and the normalized value equals the expected one (EM).
- `abstain`: abstained.
- `clarify`: asked for clarification.
- `conflict`: verification status is `conflict`.
- `hypothesis`: causal status is `hypothesis_only`, or abstained.

*Overall accuracy* is the mean correctness over all questions.

**Answer quality**
- *Exact Match / token F1*: over `value` questions.
- *Answerable accuracy*: correctness over `value` questions.
- *Unanswerable abstention accuracy*: share of `abstain` and `conflict` questions that were abstained on.
- *False-answer rate*: answered with a value that is wrong or should not have been given, divided by all questions
  (hypothesis-only answers to hypothesis questions are not false).
- *Unsupported-answer rate*: among answered questions, those whose cited answer record is not gold evidence (or which
  should not have been answered).
- *Correct abstention rate*: correct abstentions divided by all abstentions.
- *Partial-answer rate*: answered with verification status `partial`.
- *Cross-stage* and *temporal/version accuracy*: correctness on questions flagged `cross_stage` and `temporal_sensitive`.

**Evidence** (questions where retrieval ran)
- *Recall@K / Precision@K*: gold evidence IDs among the returned records (K = top-k plus the linking-record closure).
- *MRR*: reciprocal rank of the first gold record.
- *Evidence P/R/F1*: cited records vs gold evidence, over answered `value` questions.
- *Relationship recall*: gold relationship IDs found among the relationships the verifier used or the retriever traversed.

**Memory**
- *Write rate*: share of records retained. *Retention ratio*: retained bytes / candidate bytes.
- *Relevant-evidence retention*: share of test gold evidence records retained (test labels used for scoring only).
- *Rare-event retention*: retention of records whose category (event type + key observation) has frequency below 1% in
  the **training** stream. *Useful rare*: the rare records that are also gold evidence.
- *Irrelevant retained fraction*: share of retained records that no test question needs.
- *Gate test P/R/F1, AUC, AP, Brier, ECE*.

**Controller**
- *Trigger rate*: retrievals divided by questions.
- *Unnecessary retrieval*: retrieved, divided by questions where `initial_sufficient` holds.
- *Missed retrieval*: not retrieved and not clarified, divided by questions where `retrieval_required` holds.
- *Initial support rate*: share of initial answers with status `supported`.
- *Improvement after retrieval*: mean(EM_final − EM_initial) over retrieved `value` questions.

**Verification**
- *Evidence-grounding rate*: answered `value` questions whose cited answer record is gold evidence.
- *Unjustified causal-claim rate*: share of `hypothesis` questions answered with a documented or unverified causal claim.
- *Incorrect association rate*: wrong value answers citing a non-gold record, divided by answered questions.
- *Conflict detection precision/recall*.

**Discarded evidence**: over `value` questions whose gold evidence is not all available (retained or in the initial
context), the abstention rate and the wrong-answer rate.

**Efficiency**: per-stage latency (mean, p50, p95), SQLite and FAISS file sizes, retained bytes and record counts.

**Uncertainty**: 95% bootstrap CI (2,000 resamples) for accuracy and EM; exact McNemar tests on paired correctness.

## Context-growth experiment: Baseline Mamba vs AgentMamba (log benchmark)

**Question.** As the amount of ingested history grows, does AgentMamba (persistent memory + conditional retrieval +
verification) answer log-investigation questions more accurately, with better grounding and fewer unsupported
claims, than the same frozen Mamba answering from its context alone? Every part of the protocol below was fixed
before the test run (`config/experiments.yaml`, `context_growth`).

**Data.** `data/log_benchmark/v1` (`scripts/generate_log_benchmark.py`, seed 2026). It is fictional data in
operational-log formats (see `docs/DATASET_CARD.md`). There are 8 scenarios, each a plant area with its own
equipment namespace, split by scenario: dev = P4, P7, P8 (45 questions); test = P1, P2, P3, P5, P6 (75 questions).
There are 15 fixed question families: 3 exact-value lookups, 3 free-text phrase lookups, 4 should-abstain, 1
conflict, and 4 paraphrases of answerable families written to probe wording robustness. Gold answers and evidence
IDs are in `annotations/`, which is separate from the record files.

**Stages (cumulative, arrival order).** Per scenario, about 20 / 340 / 450 / 1,920 records are available after
stages 1–4:
1. The incident day.
2. The following days, with sibling equipment using the same alarm text and an exact re-delivery of an alarm file
   (3 duplicates).
3. Older history, older inspections with other findings, and a long manual.
4. Six weeks of later logs, a later inspection, and a later trip with a confirmed cause on another date.

**Memory.** A fresh store per scenario under `storage/experiments/context_growth/<run>/<scenario>/`. Stage files go
through the normal ingestion pipeline under an explicit store-all policy (the learned gate is not validated on log
records). Snapshots are kept after each stage.

**Shared initial context.** For each question at each stage, every condition receives the same records: the most
recently arrived records, as whole records, that fit a 768-token window (Mamba tokenizer, 128 tokens reserved). The
window does not depend on the question.

**Conditions**

| condition | retrieval | verification | context available to the answerer |
|---|---|---|---|
| `baseline_mamba_768` | none | none | the 768-token window |
| `baseline_mamba_2048` | none | none | a 2048-token window (larger baseline context) |
| `agentmamba_no_retrieval` | never | yes | the 768-token window |
| `agentmamba_no_verification` | conditional | no | window + retrieved records |
| `retrieval_always` | always | yes | window + retrieved records |
| `agentmamba` (proposed) | conditional | yes | window + retrieved records |
| `agentmamba_vector_only` (stage 4 only) | conditional, FAISS channel only | yes | window + retrieved |
| `agentmamba_lexical_only` (stage 4 only) | conditional, identifier/text + relationship channels | yes | window + retrieved |

Fixed across conditions:
- **Model:** the frozen `state-spaces/mamba-130m-hf` in float32 on CPU. No sampling: answers are candidate spans
  ranked by mean token log-probability.
- **Candidates:** the same candidate extractors.
- **Other settings:** the same query parser, embedding model and seed.

The baseline is not prompted or configured differently to make it weaker. It uses the same answer mechanism as
AgentMamba's answer stage, without memory, retrieval and verification. **This is an architecture-level comparison.**
It does not show that the Mamba network itself improves: Mamba's weights and scoring are identical in every condition.

**Scoring** (`src/agentmamba/evaluation/comparison.py`). Answers are normalized: lower-cased, commas removed,
whitespace collapsed, numbers compared numerically.

Correctness by family:
- **Exact-value families:** exact match.
- **Phrase families:** the gold phrase is contained in the answer (quotes are capped at 400 characters).
- **Abstain families:** the system abstained.
- **Conflict family:** status `conflict`.

Reported measures:
- *Grounded accuracy* also requires the cited answer record to be gold evidence.
- *Unsupported claims*: answered when the gold says abstain/conflict, or the answer record is not gold evidence.
- The baseline's "no candidate" outcomes are counted as abstentions but reported separately (`no_candidate_rate`):
  they are not verified abstentions.
- *Evidence in context*: share of questions whose required evidence lies inside the initial window. This is the
  measured mechanism behind any baseline degradation.
- *Recall@k / Precision@k / MRR* over retrieved records.
- *Latency* is reported over "cold" rows only (no Mamba score-cache hit). The dev and test runs ran concurrently
  on the same 12-core CPU, so absolute latencies include contention.

**Confidence.** Four separate quantities are kept apart:
1. **`candidate_share`:** Mamba's softmax share of the answer among the distinct candidate values. It is
   model-derived and uncalibrated, and it is trivially 1.0 when only one candidate was ranked (flagged).
2. **Verification status:** categorical evidence support.
3. **Retrieval max similarity:** retrieval quality, not answer confidence.
4. **Calibrated confidence:** a per-condition logistic calibrator (features: candidate share, share missing,
   verified/partial, retrieval triggered) fitted on the **dev** rows (`artifacts/calibration/logbench/`) and applied
   to test. Brier score, ECE (10 bins) and reliability bins are reported for the raw share and for calibrated
   confidence, over answered questions.

**Statistics.** Paired differences (B − A) over (question, stage) pairs, with 2,000-resample bootstrap 95% CIs and
exact McNemar tests. The four stages of one question and the questions of one scenario are correlated, so CIs and
p-values are indicative only. There is no multiple-comparison correction.

**Commands**
```powershell
$py = ".\.venv\Scripts\python.exe"
& $py scripts\generate_log_benchmark.py                                  # deterministic; --force to regenerate
& $py scripts\run_context_growth.py --split dev  --tag mamba --threads 6  # development + calibrator fit
& $py scripts\run_context_growth.py --split test --tag final --threads 6  # final report
& $py scripts\run_context_growth.py --split dev --answerer first_candidate --scenarios P4   # quick smoke test
& $py scripts\compare_runs.py <old_run_dir> <new_run_dir>                 # regression check of steel runs
```
A run can be continued with `--resume <run_dir>`. Outputs go to `experiments/results/<stamp>_context_growth_<split>_<tag>/`:
- `config.json` (conditions, models, environment, benchmark manifest)
- `ingestion.jsonl` (per stage: received, chunks, written, duplicates, records available, timings)
- `predictions.jsonl` (raw outputs, written **before** gold is read)
- `rows.jsonl` (scored rows)
- `summary.json` and `summary.md`

The steel benchmark also gained `A_baseline_mamba` (no retrieval, no verification, the question's designed initial
context) in `config/experiments.yaml`.

**Deviation, recorded.** The dev and test runs were first started concurrently (6 threads each). After about 2.5 h,
both processes held about 6 GB private memory with about 1.6 GB resident. The machine (15.7 GB, most of it used by
other applications) paged heavily and both runs stalled simultaneously several times (gaps of 5–37 minutes).

- **Cause:** each 2048-token prefill materialized logits for every prompt position (2048 × 50,280 floats), and the
  reference CPU scan keeps large full-sequence intermediates.
- **Fix:** `score_candidates` now requests only the last position's logits (`logits_to_keep=1`) and releases
  intermediates. Scores are mathematically unchanged; I verified they match the full forward pass to within 1e-5.
- **Restart:** both runs were stopped and continued with `--resume`, one scenario per fresh process, sequentially
  (dev first, so the calibrators exist before test is scored).
- **Effect on results:** predictions already written were kept. They are deterministic (same model, same prompts),
  so answers are unaffected, but their recorded latencies include the paging stalls. Latency claims therefore use
  the separate cold-cache benchmark (`scripts/benchmark_compare_latency.py`), run after the experiment with nothing
  else running.

**Host suspensions.** Some gaps in the logs were not memory pressure. One request took 4,055 s of wall time for
24 s of CPU, and a 3-hour gap (P7, 07:00–10:00) occurred while nobody used the machine. These are Windows
background-process throttling and idle sleep suspending the run.

From then on, `run_context_growth.py` and `benchmark_compare_latency.py` call
`reproducibility.disable_background_throttling()` at start-up, which does three things:
- opts the process out of power throttling;
- requests that the system stay awake while the process runs (`SetThreadExecutionState`, released on exit);
- raises the process to above-normal priority.

These settings change only execution speed, never outputs. Latencies recorded inside these runs are not used for
claims.

## Stage-1 / stage-2 protocol (CP-17) and the comprehensive metric suite

**Why it was added.** On 2026-10-29 the user reported three failures in the dashboard comparison:
the baseline receiving one arbitrary record, AgentMamba reporting vector hits but zero selected records,
and no clean demonstration of retrieval being skipped. Three causes were found by reproduction on a
clean profile:

1. **Plain-text logs were read as prose.** A `.txt` log has no blank lines, so it was cut into
   800-character chunks mid-line, with no timestamps or equipment IDs. The baseline then answered with
   the file's header comment.
   - *Fix:* `.txt`/`.md` files whose non-comment lines are at least 80% timestamped entries are parsed
     one record per line (`load_text_log`).
   - The record text is the verbatim line, the source reference is `#line=N`, and fields are parsed
     without changing values: `KEY=value`, `log_level`, `log_source`, and timezone offsets kept.
2. **The date filter was invisible.** For untyped questions, the stated date filters every retrieval
   channel. Records from other dates were removed, but the dashboard did not show this.
   - *Fix:* `retrieval_stats` now reports `n_removed_by_date_time_filter` and `n_text_hits` next to the
     vector and relationship hits and the selected count.
3. **The word "trigger" was not recognized as question vocabulary.** "triggered" was required as a
   content term, so no record could cover it.
   - *Fix:* "trigger" was added to the generic question vocabulary.
   - **Disclosure:** this word also caused the 0% `alarm_paraphrase` family on the log-benchmark *test*
     split. The fix was motivated by the user's protocol question, not tuned on test. Nevertheless, the
     log-benchmark test split can no longer evaluate this change cleanly; re-scoring it would need new
     scenarios.

Also changed:
- Verbatim log lines are rendered in prompts without a duplicated timestamp/type prefix.
- Answer candidates exclude only the identifiers *asked about*, so another ID can be an answer (e.g. a
  work-order number).
- AgentMamba responses carry an explicit `sufficiency` block: decision, reason, method.

**Protocol** (`data/protocols/cp17_context_growth/`). The user's `agentmamba_context_growth_protocol.json`
was not found on this machine, so `protocol.json` was written to replace it. It was fixed before any run.
- **Data:** the user's two synthetic stage files are copied in, with SHA-256 checks.
- **Questions:** five, asked after each stage — 3 answerable (value, work order, timestamped reading)
  and 2 unanswerable (confirmed root cause, repair completion).
- **Gold:** answers in `annotations/gold.json`, with evidence given as source line numbers.
- **Shared context:** both systems get the same 2048-token recent-arrival window. At 768 tokens the
  10-line incident cannot fit: it is about 1,050 Mamba tokens.

```powershell
& $py scripts\run_protocol.py                       # clean profile storage/profiles/protocol_cp17_context_growth_mamba
& $py scripts\run_protocol.py --answerer first_candidate --policy store_all   # 30-second smoke run
```
- Mamba and MiniLM are loaded once, and their load time is reported separately.
- The Mamba score cache is disabled, so every latency is a real computation.
- When AgentMamba skips retrieval, the same query is re-run with retrieval forced. The difference is
  reported as `time_saved_by_skipping_s`; the forced answer is never used.
- Results are written to `experiments/results/<stamp>_protocol_.../` and to the evaluation-results store.
- This is a **diagnostic** on one scenario, not a benchmark.

**Metric suite** (`src/agentmamba/evaluation/metrics_suite.py`). Every metric reports value, n and
definition. Undefined or inapplicable metrics are `None` (N/A), never 0.

| group | metrics | denominator |
|---|---|---|
| answer generation | EM, token F1, ROUGE-1, ROUGE-L, BLEU-1 (clipped unigram precision × brevity penalty) | answerable questions; an abstention is scored as an empty answer |
| answer outcomes | correct-answer rate; incorrect-answer rate | all questions |
| | unsupported-answer rate | answers |
| | correct-abstention rate | unanswerable questions |
| errors | answer error = not correct; false answer = answered wrong; abstention error = abstained | answerable questions (answer error = false answer + abstention error) |
| | unsupported-claim rate | answers |
| | retrieval failure: required evidence not in the initial context and not retrieved (N/A for systems that never retrieve) | questions needing retrieval |
| | evidence miss: required evidence neither in context nor retrieved | questions with required evidence |
| | Brier, ECE (only with calibrated probabilities and at least 20 answers) | answers |
| evidence | grounded-answer rate (correct and citing required evidence) | answerable questions |
| | evidence coverage | questions with required evidence |
| retrieval | NDCG@10, MAP@10, Recall@10, Recall@1, Hit@1/3/10 against gold evidence IDs | questions where retrieval ran |
| | trigger rate | all questions |
| | unnecessary retrieval: retrieved although evidence was already in context | questions whose evidence was in context |
| efficiency | total, mean, median, P95 (at least 20 observations), generation, retrieval, verification | queries, warm model; model load reported separately |

**Composite score** (weights in `config/default.yaml`, `evaluation.composite`). Components are normalized
to [0, 1], higher is better:
- answer quality = mean(correct-answer rate, F1, ROUGE-L), weight 0.4;
- grounding = mean(grounded-answer rate, 1 − unsupported-answer rate), weight 0.3;
- retrieval = mean(NDCG@10, Recall@10), weight 0.15;
- efficiency = 10 / (10 + median latency in s), weight 0.15.

A component a system lacks (retrieval, for the baseline) is dropped and the weights renormalized; it is
never scored as 0. `composite_shared` uses only the three components both systems have. The composite is
always shown next to the individual metrics, never instead of them.

**Benchmark metrics without re-running.** `scripts/compute_metric_suite.py --run <context-growth run>`
recomputes the suite from the stored scored rows.
- The 2026-10-27 test predictions were produced by commit 9243336, before the changes above.
- In-run latencies there are not comparable: score-cache hits plus host stalls. So efficiency for the
  systems in the cold-cache benchmark comes from `latency_cold.json`; the suite records its source.

**Evaluation-results store.** `experiments/evaluation_results.sqlite3` is separate from every operational
memory. It holds runs, per-question rows (predictions, references, evidence IDs, retrieval decisions,
verification, confidence, latency) and metric suites.
